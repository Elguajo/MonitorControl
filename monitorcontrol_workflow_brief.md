## 1. Контекст и железо

- Mac — основная рабочая система. Монитор: **LG 29WK600** (ultrawide, входы: HDMI1, HDMI2, DisplayPort; DDC/CI поддерживается).
- Отдельный ПК с **Windows** подключён к одному из HDMI монитора. Mac подключён к монитору отдельно (точный порт Mac определяем эмпирически в Фазе 1, не угадываем).
- Сейчас в macOS внешний LG сделан **основным** дисплеем — меню-бар и рабочие окна на нём.
- База проекта — open-source приложение **MonitorControl** (Swift, menu-bar app), уже склонировано в папку проекта. Базовая регулировка яркости LG по DDC на этой связке работает.

## 2. Что строим (Scope)

**Фича A — Планировщик яркости.**
Автоматически менять аппаратную яркость монитора по расписанию: утром выше, вечером ниже. Значения и время меняются из UI приложения (слайдеры/поля), не в коде.
- Дефолты (пользователь меняет потом): **09:00 → 96%**, **19:00 → 65%**, плавный переход.
- Менять яркость по DDC (VCP `0x10`), переиспользуя существующий механизм яркости MonitorControl. Не программный оверлей.

**Фича B — Главный дисплей в зависимости от состояния монитора.**
Приложение должно правильно реагировать на три разных события (детали в разделе 5):
- монитор переключили на Windows → сделать встроенный экран MacBook главным;
- монитор вернули на Mac → вернуть LG главным;
- монитор просто **уснул** → НЕ устраивать перетасовку окон (это отдельный баг macOS).

**Вне scope (не реализуем в этом приложении):** борьбу с перетасовкой окон при засыпании через виртуальные дисплеи. Это специализация BetterDisplay; вероятно отдадим сон ему. Здесь задача Фичи B по сну — **не мешать** и не срабатывать ложно, а не «чинить» сон самим.

## 3. Success criteria (как поймём, что готово)

Фича A:
- В заданное утреннее время яркость LG по DDC доходит до 96%; в вечернее — до 65%; оба значения и времена меняются из UI и сохраняются между перезапусками.
- Переход плавный, не мгновенный скачок.

Фича B:
- После переключения монитора на вход Windows встроенный экран MacBook становится главным в течение ~3–5 сек, и окна возвращаются на него.
- После возврата монитора на вход Mac LG снова становится главным.
- **Засыпание монитора НЕ запускает логику «сделать встроенный главным»** — сон должен отличаться от смены входа.
- Реальное отключение кабеля не ломает приложение.

Общие (регрессии):
- Существующий функционал MonitorControl (ручная яркость, громкость, контраст, OSD) продолжает работать без изменений.
- Сборка проекта остаётся «зелёной» (компилируется без ошибок).
- Работает и на Apple Silicon, и на Intel.

## 4. Constraints (жёсткие ограничения)

- **Переиспользовать существующий слой DDC** MonitorControl, не писать свой и не дублировать. Поддержать обе архитектуры.
- Смена главного дисплея — только через **публичные CoreGraphics API** (`CGBeginDisplayConfiguration` / `CGConfigureDisplayOrigin`; главный = дисплей с origin (0,0)). Хранить и применять две раскладки: «LG главный» и «встроенный главный».
- **Никаких хардкод-значений входов** монитора (VCP `0x60`) без эмпирической проверки — у LG значения нестандартные, определяются в Фазе 1.
- Изменения модульные и обратимые; не ломать текущий функционал; после каждого шага объяснять простым языком, как проверить результат.

## 5. Сценарии для Фичи B (логика «сторожа»)

| Событие | Сигнал в macOS | Что делает приложение |
|---|---|---|
| Монитор → вход Windows | НЕТ события отключения; дисплей остаётся в списке, но DDC `0x60` показывает чужой вход / не отвечает | Сделать встроенный экран главным |
| Монитор → обратно на Mac | DDC снова отвечает, вход = порт Mac | Вернуть LG главным |
| Монитор уснул | Приходит настоящее событие отключения (`CGDisplayRegisterReconfigurationCallback`) | Ничего не промоутить; не мешать, при пробуждении не тасовать |
| Кабель выдернули | Настоящее отключение, не возвращается | Оставить поведение macOS как есть |

**Ключевое правило:** «сделать встроенный главным» срабатывает **только** по сигналу смены входа (без события отключения), а не по событию отключения. Иначе приложение будет ложно срабатывать на каждый сон.

## 6. Обязательные проверки (Required checks)

То, что должно быть проверено перед сдачей каждого куска:
- проект собирается (`xcodebuild`) без ошибок;
- ручная яркость/громкость/контраст и OSD MonitorControl не сломаны;
- перечислены и обработаны граничные случаи state machine сторожа: быстрый сон↔пробуждение, смена входа во время сна, выдёргивание кабеля пока монитор на Windows, наличие более чем двух дисплеев;
- нет «магических» чисел входов без обоснования из логов Фазы 1;
- оба пути (Apple Silicon и Intel) покрыты.

## 7. РУЧНЫЕ ГЕЙТЫ (то, что Claude и subagent'ы сделать не могут)

Эти шаги требуют живого Mac + подключённого LG; их выполняю я, агенты — нет:
- **Диагностика на железе (Фаза 1):** запустить тестовый инструмент, вручную переключить монитор на Windows и обратно, отдельно усыпить и разбудить монитор, собрать логи. Логи определяют, какой механизм детекции реально работает.
- **Решение по сну:** на основе логов — гасим перетасовку при засыпании силами BetterDisplay или нет. Без этого Фазу B по сну не финализировать.

## 8. Порядок работы (фазы)

> В конце каждой фазы: Claude показывает план → я подтверждаю → Claude реализует → объясняет, как проверить.

- **Фаза 0 — Разведка кодовой базы.** Найти и показать: где вызывается DDC (вкл. `MonitorControl/Support/Arm64DDC.swift` для Apple Silicon и общий `DDC.swift`), точку входа приложения, как устроены настройки и меню, где управляется раскладка дисплеев. *(Хороший кандидат на dynamic workflow.)*
- **Фаза 1 — Диагностический тест (РУЧНОЙ ГЕЙТ).** Claude пишет маленький инструмент, который логирует события `CGDisplayRegisterReconfigurationCallback` и параллельно раз в ~1 сек читает VCP `0x60`. Я прогоняю сценарии (Windows туда-обратно; сон-пробуждение) и приношу логи. Выбираем механизм детекции по фактам.
- **Фаза 2 — Фича A (планировщик яркости).** Низкий риск, обычная сессия Claude Code.
- **Фаза 3 — Фича B (сторож + смена главного дисплея)** по результатам Фазы 1. Обычная сессия.
- **Фаза 4 — Состязательный стресс-тест state machine** сторожа: агенты пытаются сломать логику на граничных случаях из раздела 6. *(Хороший кандидат на dynamic workflow.)*

## 9. Где dynamic workflow, а где обычная сессия

- **Dynamic workflow уместен:** Фаза 0 (разведка большой базы параллельно) и Фаза 4 (адверсариальный разбор edge-кейсов). Это формы «исследование/аудит», под которые он сделан.
- **Обычная сессия лучше:** Фазы 2 и 3 — это пара небольших модулей, workflow тут только сожжёт лишние токены и всё равно не проверит поведение монитора.
- **Никогда не отдаём агентам:** ручные гейты из раздела 7 — их закрывает только запуск на твоём железе.
